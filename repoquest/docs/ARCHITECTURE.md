# RepoQuest architecture

This document explains how RepoQuest is put together, so you can find your way around the code and change it with confidence.

## Principles

1. **Never present a guess as a fact.** Relationships are *confirmed* (backed by a statement in source) or *inferred* (naming convention), and the UI always says which.
2. **Cite sources.** Every summary fact carries the file or API it came from.
3. **Work without AI.** AI is an optional layer on top of the deterministic analysis.
4. **Keep analysis pure.** Everything in `src/lib/analysis` is a pure function of fetched data, so it can be unit-tested without a network.
5. **Be gentle with GitHub.** Use a small, fixed number of API calls per repository and cache aggressively.

## Stack

| Concern | Choice | Why |
|---|---|---|
| Framework | Next.js 16 (App Router), React 19, TypeScript | Server Components fetch on the server, so tokens never reach the browser. Also gives free Vercel hosting. |
| Styling | Tailwind CSS v4 with tokens in `src/app/globals.css` | Small, consistent design system |
| Diagrams | `@xyflow/react` (React Flow) | Accessible, zoom/pan, custom nodes |
| Layout | A small layered layout in `graph.ts` | Avoids a dagre/elk dependency |
| Parsing | Regex import extraction in `imports.ts` | Tree-sitter WASM grammars are several MB per language. Regex plus file-existence checks keeps "confirmed" honest. |
| AI | `@anthropic-ai/sdk`, or Ollama via HTTP | Optional and server-only |
| Tests | Vitest | Fast, ESM, TypeScript-native |

## Request flow

```
/r/owner/repo
  └─ analyzeRepo(owner, repo)            React cache(): one fetch per request (page, metadata, OG image share it)
       └─ fetchRepoData()                 lib/github/repo.ts
            ├─ GET /repos/{o}/{r}                         metadata, default branch
            ├─ GET /repos/{o}/{r}/git/trees/{branch}?recursive=1
            ├─ GET /repos/{o}/{r}/readme
            ├─ GET /repos/{o}/{r}/languages
            ├─ GET /repos/{o}/{r}/issues (good first issue + recently updated)
            ├─ raw.githubusercontent.com: manifests (package.json, tsconfig, pyproject, Cargo.toml, go.mod, Makefile…)
            └─ raw.githubusercontent.com: ≤80 selected source files (10 concurrent)
       └─ assembleAnalysis(raw)           lib/analysis/assemble.ts (pure)
            ├─ detectEntryPoints          manifests (confirmed) + filename conventions
            ├─ buildArchitecture          imports → file deps → module edges; inferred test/example edges
            ├─ computeLanguages           GitHub byte counts, or tree sizes as fallback
            ├─ buildSummary               facts with sources; traceExecutionFlow
            └─ rankIssues                 content-based assessment
```

All `fetch` calls use `next: { revalidate: 1800 }`, so repeat visits within 30 minutes cost no API quota.

### File selection

`selectFilesToAnalyze` picks entry points first, then round-robins across modules (shallow files, `index`/`main` files first; tests, docs, and examples last). The architecture map then covers the whole project instead of the first folder alphabetically.

### Modules

`moduleOf(path)` groups files into modules: root files → `(root)`; `docs/x` → `docs`; container folders go one level deeper (`packages/foo`, `src/lib`), and nested containers one more (`src/lib/github`, `src/components/forms`). The graph keeps at most 36 modules, preferring connected and entry-point modules.

### Import resolution

`extractImports` strips comments, then matches language-specific statements. `resolveImport` maps a specifier to a path **only if that file exists in the tree**:

* JS/TS: relative paths, extension inference (`./a` → `a.ts`, `./a.js` → `a.ts`), `index` files, and `tsconfig` `paths` aliases (default `@/` → `src/`).
* Python: relative (`from ..x import y`), absolute under `.`, `src/`, `lib/`, packages via `__init__.py`.
* Go: module-prefixed imports via `go.mod` → package directory.
* Rust: `mod x;` and `use crate::…`. Java/Kotlin: package path suffix. C/C++: `#include "…"`. Ruby: `require_relative`.
* HTML/CSS: `<script src>`, `<link rel=stylesheet>`, `<a href="*.html">` (recorded as a *link*, not an import), `@import`.

### Issue assessment

`assessIssue` adds and removes points for labels (beginner, help wanted, docs, blocking), body length, structure (steps, checklists), hard-work keywords, assignees, "I'm working on this" claims, locks, long threads, and staleness. A verdict of **good-first** requires a positive label signal **and** a ≥60-character description **and** no blockers. Relevant files are either *mentioned* (path appears in the issue text and exists) or a *keyword* guess (file name matches title words).

## Security

* Tokens are read only in server code (`import "server-only"` guards the GitHub and AI modules).
* `/api/file` validates owner/repo names and rejects `..`, `.`, and empty path segments. Files over 400 KB or binary files are refused.
* `/api/explain` re-fetches content on the server (it never trusts client-sent code), caches answers in an LRU, and rate-limits per IP. Prompts wrap repository content in delimiters, neutralize delimiter look-alikes, and tell the model to treat repository text as data.
* AI output is rendered by `SafeMarkdown`, which builds React elements and never uses `dangerouslySetInnerHTML`.
* Security headers (`X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`) are set in `next.config.ts`.

## Testing

* `tests/unit`: about 150 tests covering URL parsing, import extraction and resolution for every supported language, module grouping, entry points, file selection, graph building, layout, execution flow, summaries, issue verdicts, rate limiting, prompt construction, and provider selection.
* `npm run test:live`: an end-to-end import of a real repository.
* The landing demo is itself an integration test: `npm run demo:build` runs the full pipeline over this repository.
